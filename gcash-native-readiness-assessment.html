Assessment Criteria

Each component is evaluated against seven criteria. The overall status reflects the weakest criterion — a single unresolved structural issue can block Code Connect linkability even when everything else passes.

IDCriterionWhat We Check
C1Layer Structure & NamingAre layers named semantically (e.g. leading-icon, content) rather than left as Figma defaults (Frame 42, Group 7)? Is the hierarchy logical and free of unnecessary nesting?
C2Variant & Property NamingDo variants and component properties use clear, consistent conventions? Are boolean properties expressed as true/false (not yes/no)? Are enum values lowercase and hyphenated?
C3Token CoverageAre all color, spacing, typography, and radius values bound to design tokens rather than hardcoded? Token coverage determines how easily a native engineer can map design decisions to a token system.
C4Native MappabilityDoes the component map cleanly to a standard native primitive (e.g. DisclosureGroup, Button, List)? Are there web-only patterns with no native equivalent?
C5Interaction State CoverageAre all expected interactive states defined as variants — default, pressed, focused, disabled, error? Missing states force engineers to invent visual behavior.
C6Asset & Icon QualityAre icons defined as vector components (not raster/PNG embeds)? Are they colored using tokens so tinting works natively?
C7Code Connect LinkabilityIs the component a proper Figma component set? Are property names clean enough to map 1:1 to native parameters? Are Code Connect mappings registered?

A. Native Mobile Translatability

A1 — What Works Well

  • Simple horizontal row layout maps directly to HStack/Row in both platforms with no web-specific layout assumptions.
  • Collapsed/expanded toggle maps cleanly to DisclosureGroup (SwiftUI) or AnimatedVisibility in a Column (Compose).
  • Chevron icons are confirmed Figma component instances (vector paths) — export cleanly as SVG/PDF for iOS or VectorDrawable for Android.
  • All spacing and padding values are tokenized (space/space-12, space/space-16).
  • Color tokens explicitly separate collapsed and expanded states, allowing direct 1:1 mapping to native color resources.

A2 — Issues & Recommendations

Missing Interaction States

Issue: Only collapsed and expanded states defined. Native mobile requires pressed, disabled, and focused states at minimum. Without these, engineers will invent visuals leading to inconsistency.

Recommendation: Add pressed and disabled variants with semantic tokens (e.g. main/accordion/color/pressed/bg, main/accordion/color/disabled/label). Define focused as a focus ring or border highlight.

Expanded Content Panel Not Designed

Issue: Only the header row is designed. The revealed content panel — its padding, background, and divider — is absent. This is part of the component contract in native implementations.

Recommendation: Add a content slot to the expanded variant with defined vertical padding, background token, and bottom divider treatment. The slot should accept arbitrary child content natively.

Custom Fonts — Device Availability

Issue: Label uses "Proxima Soft" and description uses "BarkAda" — neither are system fonts on iOS or Android and must be bundled.

Recommendation: Confirm both fonts are bundled in native apps. Map tokens to UIFont(name:) / Font.custom() on iOS and fontFamily in the Compose theme on Android.

A. Native Mobile Translatability

A1 — What Works Well

  • All three style variants map naturally to standard native primitives. The base and with stroke styles map to a List row (SwiftUI) or LazyColumn item (Compose). The corner radius style maps to a card-style Button or Surface.
  • Drop shadow on the base style is achievable with .shadow(color:radius:x:y:) in SwiftUI or Modifier.shadow(elevation:) in Compose — the shadow values (0px 1px 3px rgba(232,238,242,0.79)) are low-profile and will translate naturally.
  • The bottom border on the with stroke style maps cleanly to a Divider view in SwiftUI or a HorizontalDivider in Compose.
  • Corner radius of 6px (radius/radius-2) is a tokenized value and maps directly to .cornerRadius(6) or RoundedCornerShape(6.dp).
  • Chevron Right is a confirmed vector component instance — exports cleanly for all native targets.

A2 — Issues & Recommendations

No Interactive States

Issue: This is a tappable row but has zero interactive state variants — no pressed, disabled, or focused. This is the most significant gap in the component. Engineers building native implementations will have to invent the visual feedback for tap, which leads to fragmented UX across the app.

Recommendation: Add a state property with at minimum default, pressed, and disabled values. Apply per-style token overrides where needed (e.g. main/action-list/color/pressed/bg). The pressed state on a list row is typically a light background tint, which is simple to design and critical to have.

Label Color Inconsistency Across Styles

Issue: The corner radius style uses main/action-list/color/default/label-brand (#005CE5, blue) for its label, while base and with stroke use main/action-list/color/default/label (#0A2757, navy). This is an intentional design difference, but it is undocumented and may confuse engineers who expect consistent label color across styles.

Recommendation: Add a component annotation or Figma description clarifying this is intentional — the corner radius style is a standalone CTA-like element that uses brand blue to signal interactivity. If this is not intentional, standardize to a single label color token.

Style Variant Names Contain Spaces

Issue: Style values with stroke and corner radius contain spaces, which are not compatible with most Code Connect prop-mapping conventions and many code style guides (Swift/Kotlin enums do not allow spaces).

Recommendation: Rename to hyphenated or camelCase values: base, with-stroke, corner-radius — or map to native enum values explicitly in Code Connect: "with stroke" → .withStroke / WithStroke.

Drop Shadow Uses a Non-Semantic Effect Token

Issue: The base style shadow is defined via Depth/D0, which resolves to a hardcoded RGBA color (rgba(232,238,242,0.79)). This is a generic depth token, not a component-specific semantic token. It will be harder to maintain across theme changes.

Recommendation: Introduce a semantic shadow token like main/action-list/effect/default/shadow that maps to Depth/D0 internally. This decouples the component from the generic depth system and makes it easier to theme or update independently.

A. Native Mobile Translatability

A1 — What Works Well

  • Semantic color token coverage is the strongest seen so far — all five types (Default, Information, Warning, Error, Success) have dedicated tokens for bg, border, label-title, description, icon, and label-link. This maps directly to a native token switch by alert type.
  • Non-Full Width variants use a left-side colored border (border-l-6) combined with a rounded corner radius (radius/radius-1, 4px) — this maps cleanly to a native overlay(alignment:) or a background + clipShape in SwiftUI, or a border + shape in Compose.
  • The five-type structure maps naturally to a native enum: AlertType { default, info, warning, error, success }. Color and icon selection can be driven from this enum in a single switch statement.
  • Full Width variants (edge-to-edge) and container variants (with padding/rounded corners) represent distinct layout contexts that can be expressed as a single isFullWidth: Bool parameter in native code.
  • The "Learn More" link and chevron in non-Full Width variants is a clean optional CTA slot — maps to an optional action: (() -> Void)? in SwiftUI or a nullable onLearnMore: (() -> Unit)? in Compose.

A2 — Issues & Recommendations

Alert-Type Icons Are Raster Assets — Critical

Issue (Critical): The semantic type icons — Information circle, Warning triangle, Error circle with exclamation, and Checkmark — are rendered as raster images (Figma CDN asset URLs: imgShapeFull, imgVector2107, imgEllipse2098, etc.). They are not Figma component instances. Raster assets cannot be tinted using the main/alert/color/{type}/icon tokens at runtime, will not scale on high-density screens, and will not export correctly as SVG/VectorDrawable for native targets.

Recommendation: Replace all four type icons with proper vector icon components from the GCash icon library, with their fill color bound to the corresponding main/alert/color/{type}/icon token. The leading icon slot (Left Icon=yes) also uses the same generic grey circle placeholder as the Accordion — this should also accept a real icon component.

showHeader Prop Has No Figma Variant

Issue: The generated code exposes a showHeader boolean prop that controls whether the title text renders. This prop has no corresponding Figma variant property — it is a code-only construct. Engineers cannot control or preview this behaviour through Figma variants or Code Connect.

Recommendation: Either add a Title boolean variant property to the component set (mirroring the existing Description property), or remove the internal showHeader prop and instead drive title visibility through the existing Description=yes/no logic. Either path resolves the Figma/code mismatch.

Title Font Size Inconsistent Across Layout Modes

Issue: Full Width variants use font-size/font-size-25 (16px) for the title, while non-Full Width variants use font-size/font-size-30 (18px). This is a visual inconsistency — the same "alert title" text is larger in the container (non-full-width) layout than in the edge-to-edge layout. It is unclear if this is intentional.

Recommendation: If intentional, add a Figma annotation explaining the typographic difference and expose it via a dedicated text style token (e.g. main/alert/typography/title-inline vs main/alert/typography/title-banner). If unintentional, standardise to a single size.

Full Width Boolean Uses Mixed-Case Strings

Issue: The Full Width property uses yes (lowercase) and No (capitalised) — inconsistent casing within the same boolean property. This inconsistency will produce unreliable Code Connect mappings and is a data-quality issue in the Figma file.

Recommendation: Standardise to true/false to match the same fix needed in the Accordion and List components.

Hardcoded opacity-80 on Non-Full Width Descriptions

Issue: Description text on non-Full Width (container) variants applies opacity: 0.8 as a hardcoded layer property. This is not expressed through a token and will not be visible in a token inspection tool. It also means the effective rendered colour differs from the raw description token value.

Recommendation: Either absorb the opacity into the description color tokens directly (e.g. adjust the hex value to the 80% blended equivalent), or create a composite token that includes the opacity. Remove the hardcoded layer opacity.
