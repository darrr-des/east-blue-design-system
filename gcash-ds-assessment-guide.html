This document is the unified assessment guide for evaluating GCash Design System components across two dimensions: DS Health (should this component exist in the core DS? Is it well-structured?) and Native Mobile Readiness (can it be implemented in SwiftUI and Jetpack Compose?).

Assessment results are published as a modular HTML report — each component lives in its own .html source file, and a build script assembles them into a single index.html with minified CSS. See the HTML Report Architecture section for details.

Use this guide as your first-message context when starting a new Claude assessment session.

What You Are Assessing

Every component is evaluated across two phases. Both must be completed for each component.

Phase 1
DS Health (Debloat Audit)
Is this component worth keeping in the core DS? Is it well-designed?
Phase 2
Native Mobile Readiness
Can this component be handed off to engineers for SwiftUI and Jetpack Compose implementation?

These are complementary but distinct. A component can pass Phase 1 (belongs in DS) but fail Phase 2 (raster icons, broken token coverage). Both must be assessed.

Phase 1: DS Health — The 4 Traits

Every component is evaluated against these four traits. Rate each as ✅ Pass · ⚠️ Needs work · ❌ Fail.

TraitWhat to Check
ReusableDoes this component work across multiple contexts and flows, not just one specific screen or feature?
Self-containedDoes it carry its own styles, states, and logic without depending on external setup?
ConsistentDoes it behave predictably? Are naming conventions, property types, and state coverage aligned with the rest of the DS?
ComposableCan it be nested inside other components? Does it fit into the existing component hierarchy?
DS Health Verdicts

The overall DS Health verdict is determined by the combination of trait scores and structural findings.

VerdictMeaning
KeepAll 4 traits pass. Component belongs in core DS as-is.
FixComponent belongs in core DS but has specific issues (missing states, naming, incomplete variants).
RestructureNeeds significant property or architectural changes before it is usable.
ConsolidateShould be merged into another component (reduce duplication).
Product LayerToo feature-specific for core DS. Move to a product-layer pattern library.
RemoveRedundant, deprecated, or doesn't belong in a design system.
Phase 2: Native Mobile Readiness — The 7 Criteria

Score each criterion independently. The overall component status is set by the worst-scoring criterion — one C6 failure makes the whole component "Requires Rework" even if every other criterion passes.

IDCriterionWhat to Check
C1Layer Structure & NamingAre layers named semantically (leading-icon, content) not as Figma defaults (Frame 42)?
C2Variant & Property NamingClean names? Booleans as true/false (not yes/no)? Enum values hyphenated?
C3Token CoverageAll colors, spacing, typography, radius bound to design tokens? No hardcoded values?
C4Native MappabilityMaps to standard native primitive (DisclosureGroup, Button, List)?
C5Interaction State CoverageAll expected states as variants: default, pressed, disabled, focused?
C6Asset & Icon QualityIcons are vector component instances (not raster/PNG)? Colored with tokens?
C7Code Connect LinkabilityProper component set? Property names map 1:1 to native params? Mappings registered?
Native Readiness Status Levels
StatusMeaning
ReadyClean structure, maps well to native, Code Connect linkable as-is.
Needs RefinementMinor naming, structural, or token issues to fix before linking.
Requires ReworkSignificant structural or design issues — needs redesign before native translation.
Not ApplicableWeb-only concept or removed-from-DS component — skip native assessment.

HTML Report Architecture

The assessment report is a modular, build-assembled static site hosted on GitHub Pages.

Repository Structure
gcash-design-system/
├── index.html                     ← Built output (do not edit directly)
├── styles.css                     ← Built output (minified)
├── README.md
└── assessment-src/
    ├── shell.html                 ← Shared layout, sidebar, cover, JS
    ├── styles.css                 ← Source CSS (unminified)
    ├── build.js                   ← Node.js build script
    └── components/
        ├── accordion.html         ← One file per component
        └── ...
How the Build Works
  1. build.js reads shell.html as the page scaffold
  2. It reads every .html file in components/ (sorted alphabetically)
  3. From each component file, it extracts 4 tagged blocks using comment markers
  4. It injects all blocks into the shell at the corresponding placeholder comments
  5. It minifies both HTML and CSS, then writes index.html and styles.css to the repo root

GCash-Specific Patterns to Check on Every Component

These issue patterns have been confirmed to recur across the GCash DS library. Use them as a checklist during every assessment.

Naming & Property Issues (C2)

Look for these naming anti-patterns on every component:

Boolean properties as strings — Should use true/false, not yes/no or any mixed-case variant. Flag every occurrence.
Space-separated variant names — Values like with stroke are incompatible with Swift/Kotlin enum naming. Should be hyphenated or camelCase.
Version numbers in variant names — Names like transaction_v1 indicate cleanup debt. Identify what differs, keep the better one, flag the rest.
Ambiguous size names — size=default is unclear. Should be small, medium, large.
Overloaded property keys — A single type encoding both visual style and layout should be split into two properties.
State values encoding style — State property with layout descriptors should be separated. State = interaction states only.
Structural Issues (C1, C4)

Look for these structural anti-patterns:

Generic layer names — Figma defaults (Frame 42, Group 7, Vector, Placeholder) should be semantic (icon-leading, content-body).
Non-component primitives — Boolean ops, flattened shapes, or bare groups where a proper component set is expected. Cannot be instanced or Code Connected.
Feature variants instead of properties — [Component] - with [Feature] should be a boolean property (hasIcon=true), not a standalone frame.
Baked-in content — Components that hardcode content into fixed variants instead of composable slots.
Token Issues (C3)

Look for these token anti-patterns:

Hardcoded opacity — opacity-80 on layers instead of a semantic opacity token.
Generic depth/shadow tokens — Shared Depth/D0 instead of component-specific semantic shadow tokens.
Raw pixel values as identifiers — Size values as raw numbers (64, 52) instead of named tokens (large, medium).
Asset Issues (C6)

Look for these asset anti-patterns:

Raster icons — Semantic icons as raster images from Figma CDN. Hard C6 blocker.
How to detect: Look for const imgXxx = "https://www.figma.com/api/mcp/asset/..." used as <img src={imgXxx} />. Semantic icon as <img> = raster.
State Coverage Issues (C5)

Check every component for these missing states:

Missing disabled state — All interactive components need a disabled variant.
Missing indeterminate state — Selection components (checkboxes, radio groups) should support indeterminate.
Missing selected / active state — Filter chips, toggles, tab-like components need a selected variant.
Incomplete state matrix — If a component has sub-types, verify every sub-type covers all relevant states.
Documentation Issues
Empty screen context panels — Components without usage examples. Flag as documentation gap and handoff risk.
Deprecated components in live templates — Must be cleaned up before deletion.
Known Good Patterns — Do Not Re-Flag

Semantic color token naming — The main/{component}/color/{state}/{role} convention is consistent and well-structured.

Chevron icons — Chevron Down, Up, Right are confirmed vector component instances.

Spacing tokens — space/space-* tokens are consistently applied.

Custom fonts — font-family/font-primary (Proxima Soft) and font-family/font-secondary (BarkAda) require native bundle verification. Flag once per session only.

Assessment Workflow (Step by Step)

For each new Figma node URL received:

Step 1
Get the metadata
Call: get_metadata(fileKey, nodeId)
Count variants, read property names/values, spot C2 issues, understand C1 hierarchy.
Step 2
Get the screenshot
Call: get_screenshot(fileKey, nodeId)
Visually confirm the component, spot missing states.
Step 3
Get full design context
Call: get_design_context(fileKey, nodeId,
  disableCodeConnect=true,
  clientFrameworks="SwiftUI, Jetpack Compose",
  clientLanguages="Swift, Kotlin")
Confirm layer naming (C1), token usage (C3), detect raster icons (C6), surface hidden props (C2/C7), assess native mappability (C4).
Step 4
Get variable/token definitions
Call: get_variable_defs(fileKey, nodeId)
Confirm token coverage (C3), extract hex values, identify missing semantic tokens.
Step 5 — Optional
Spot-check specific nodes
Call: get_metadata(fileKey, specificNodeId)
Verify vector vs. raster. <instance> = vector. <img> in step 3 = raster.
Step 6
Write the assessment
Score all 4 DS traits and all 7 native criteria. Assign verdicts. Output findings as a quick markdown summary for review.
Step 7
Produce the HTML component file
Once confirmed, create assessment-src/components/[name].html with all 4 tagged blocks.
Step 8
Build and verify
node assessment-src/build.js
Open index.html to verify. Commit and push.
Assessment Output Format

Each component assessment has two deliverables: a quick markdown summary (for chat/review) and an HTML component file (for the published report).

Use this format for in-session review before producing the HTML file:

**Native Readiness Status:** [Ready / Needs Refinement / Requires Rework / Not Applicable]

### Action Items

B. HTML Component File (for the published report)

After review is confirmed, produce the HTML file for assessment-src/components/. Must contain all 4 tagged blocks.

File naming: lowercase, hyphenated — accordion.html, list-label-only.html, bottom-sheet.html

Template reference: Use the Accordion component file as a working reference for the full HTML structure (nav item, summary card, summary row, section with dual-status header, Phase 1 trait grid, Phase 2 criteria tables, Code Connect readiness, design tokens, action items).

Post-fix (v2) components

For components partially fixed via Figma MCP, add a changelog block between Overview and Phase 1. Include tag-fixed / tag-open spans and score-delta indicators. Append a v2 Post-Fix tag to the component name.
